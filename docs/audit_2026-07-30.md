## 2. BLOQUANTS

### B1 — `metano_normal_home` ch5 : le joueur est gelé définitivement ⛔

`Data/Script/halcyon/ground/metano_normal_home/metano_normal_home_ch_5.lua`

```lua
19: function metano_normal_home_ch_5.Farewell_Cutscene()
26:   GAME:CutsceneMode(true)
27:   AI:DisableCharacterAI(partner)
...
259:  GAME:WaitFrames(40)
260:  --they leave, end cutscene.        <-- l'intention est écrite, le code manque
265:  --[[ ... 120 lignes de brouillon anglais ... ]]--
406:  SV.Chapter5.SawZigzagoonFamilyCutscene = true
408: end
```

`grep -n "CutsceneMode" metano_normal_home_ch_5.lua` ne renvoie **qu'une seule ligne : la 26**. Il n'y a ni `CutsceneMode(false)`, ni `EnableCharacterAI`, ni `EnterGroundMap`, ni `EndDungeonRun` dans tout le fichier.

Appel : `init.lua:77-83`, dans `Enter` **et** dans `GameLoad`.

Preuve moteur : `Ground/GroundScene.cs:176` — `if (DataManager.Instance.Save.CutsceneMode) yield break;` dans `ProcessInput`. Le mode est persistant (`Save.CutsceneMode`, écrit en `Lua/ScriptGame.cs:1382`). Il survit donc à la sauvegarde.

**Conséquence :** au chapitre 5, en entrant chez la famille d'Almotz, la scène se joue puis rend la main avec les entrées désactivées. Le joueur ne peut plus bouger, ni ouvrir le menu. Comme `SawZigzagoonFamilyCutscene` est posé à la ligne 406, recharger ne rejoue pas la scène — mais `CutsceneMode` est déjà dans la sauvegarde.

**Correctif (2 lignes, avant le `end` de la 408) :**
```lua
	if partner ~= nil then
		AI:EnableCharacterAI(partner)
		AI:SetCharacterAI(partner, 'origin.ai.ground_partner', CH('PLAYER'), partner.Position)
	end
	GAME:CutsceneMode(false)
```
(patron copié de `RaidScenes.lua:313-320`, déjà en place ailleurs dans le dépôt)

### B2 — `metano_electric_home_ch_5.lua` n'est jamais chargé

`Data/Script/halcyon/ground/metano_electric_home/init.lua:9-11`
```lua
require 'halcyon.ground.metano_electric_home.metano_electric_home_ch_2'
require 'halcyon.ground.metano_electric_home.metano_electric_home_ch_3'
```

```lua
end
```

### Le point le plus mal compris du dépôt — et il est correct
`GSceneZone.cs:57-66` :
```csharp
public IEnumerator<YieldInstruction> InitGround(bool saveLoad) {
    yield return ...CurrentGround.OnInit();
    if (saveLoad) yield return ...CurrentGround.OnGameLoad();
}
```
`saveLoad == true` **uniquement** depuis `TopMenu.cs:268` (Continuer). Toutes les autres entrées (`GameManager.cs:773`, quicksave ×2) passent `false`.

Donc **182 grounds sans callback `GameLoad`** n'est **pas** un bug de transition : le `GameLoad` ne sert qu'au chargement d'une sauvegarde faite *sur cette carte*. Il ne concerne que les cartes où l'on peut sauvegarder. Mon audit de premier passage l'avait signalé ; la lecture du moteur l'a invalidé. Je le note pour éviter qu'un futur agent « corrige » 182 fichiers pour rien.

De même, `moveToZoneInit` (`GameManager.cs:772`) porte le commentaire `//no fade; the script handles that itself` : c'est bien au `Enter` de chaque carte de poser le `FadeIn`. **2 cartes seulement** n'en ont aucun d'atteignable : `grand_canyon_porte` (mais sa `sortie()` ligne 47-50 fait `FadeOut` + `EndDungeonRun`, donc c'est voulu) et `testmap` (carte d'atelier).
